# The button that answered with JSON

**Shipped:** 2026-10-29
**Surface:** `routes/aiJobs.js` (`GET /ai-jobs/apply/:id`)
**Test:** `npm run test:apply-fallback` (22 checks)
**Audit:** `npm run audit:cta-coverage` (read-only, against a live site)

## What the log showed

```
19:57:20  GET /ai-jobs/apply/39fa5490-… 404 - 380ms
```

Probing that URL returned `{"error":"No destination configured for this offer"}`.
A real reader had pressed a button on a page they read to the end, and the site
answered with raw JSON. The click was not recorded either — the route returned
before it reached the tracking — so the leak was invisible in the one place that
should have shown it.

## What it does now

| Before | After |
| --- | --- |
| `404 {"error":"No destination configured for this offer"}` | a page: "Applications for this one are not open yet", the offer's name, a link back to the article and to `/ai-jobs` |
| the click vanished | counted as `apply_no_destination` (or `apply_bad_destination`), and recorded on the offer funnel as `apply_click` with `unavailable: true` |
| a missing offer dropped silently | counted as `apply_missing`, then the same 404 JSON for API clients |

A working destination still gets a `302`, and the destination is still validated
(`http`/`https` only, and only if it is trusted) before it is used. `noindex` on
the fallback page, so it cannot compete with the real offer in search.

The reason this matters commercially: an "unavailable" click is the most
valuable click in the system. It is a reader who wanted to buy something the
business forgot to connect. It now appears in the tenant's numbers instead of
looking like nobody was interested.

## The number that came out of looking

`npm run audit:cta-coverage` against production:

```
Blog index: 200, 308 article links

Button goes straight to the provider .... 191 (62%)
Button goes through this site ........... 0 (0%)   measurable
No button at all ....................... 117 (38%)   cannot convert
  ...of those, no CTA block at all ..... 96 (31%)   template never added one
```

Three facts, none of which was visible from the database:

1. **Not one page routes its button through this site.** Every tracked click the
   portal reports will come from future pages, hubs, or offer pages — never from
   the 191 that already exist. The CTR figure for those pages is not "0%", it is
   "not measured", which is why the endpoint returns `clicks_note`.
2. **117 pages (38%) have no button at all**, so they cannot convert however good
   the writing is. **96 of those have no closing block whatsoever** — the
   `contentJourney` "skills/salary" pages were generated by a template that never
   learned about the CTA.
3. The two populations want different fixes. The 191 need a tracked redirect; the
   96 need a closing block. Those are template changes and therefore re-render
   those pages (`content` untouched, `BLOG_REBUILD_STALE_PAGES=off` still applies).

## What shipped for it (same day)

The two failing populations were invisible to the migration because they were not
*stale*: `isStalePage()` only matched the pre-2026-10-29 generic footer text, and a
page with **no closing block at all** passes both the readability audit and that
check. So the boot restore had never looked at them.

`utils/ctaBlock.js` now answers the question the migration should have asked:

```js
needsClosingBlock(html)   // has an <article>, but no closing block or nothing to press
```

Used by:
- `scripts/blogManager.js` → `restoreFromDB()` rebuilds such a page on boot, from
  its stored `content`, exactly like the old-footer migration does. `BLOG_REBUILD_STALE_PAGES=off`
  still disables it. The log line says which reason fired:
  `[DB] Rebuilt <slug> (no closing block)`.
- `scripts/repair_blog_html.js` → dry-run now lists them, so you can see the list
  before anything is rewritten: `npm run repair:blog-html`.
- `scripts/audit_page_fidelity.mjs` → new count,
  `no closing block / nothing to press … N`, and still verifies the prose is
  byte-identical to `content` for every page.

**The convergence rule.** A predicate that disagrees with the template rebuilds the
same page on every single boot, forever. `ctaBlock()`'s no-destination branch used
to emit a block with nothing to press — precisely what the new predicate calls
broken. It now ends with `<a class="cta-btn cta-btn--alt" href="/ai-jobs">Browse
other opportunities</a>`, so every branch of the template satisfies the predicate
and the repair reaches a fixed point on the first pass. `test:blog-html` asserts
this against the built page, the no-destination page and a page with no offer at
all.

## What to expect on the next deploy

Up to 117 pages rebuild once (frames only — `content` untouched, verified by
`audit:page-fidelity`). To see the list before trusting it:

```bash
npm run repair:blog-html        # dry run: lists every page it would rebuild, and why
npm run audit:page-fidelity     # prose identical / differs / no closing block
npm run audit:cta-coverage      # after the deploy: no-button count should be 0
```

**The second boot is the one that matters.** A rebuild that does not converge
rewrites the same pages on every deploy, and the site still looks fine while it
happens. That is now a test rather than a hope:

```bash
npm run test:boot-convergence   # 11 checks: boot 1 repairs, boots 2-5 do nothing
```

It boots a corpus of stored pages — no block, block with no button, old footer,
unreadable, no `<article>`, no `content`, healthy — through the same
`pageNeedsRebuild()` the restore calls, and asserts the second boot rebuilds
zero pages across 30 offer-type × destination combinations. I proved the test is
not vacuous by removing the no-destination button from `ctaBlock()`: four checks
failed with the exact pages named, then passed again on restore. On Render, the
equivalent check is the boot log: the first deploy prints
`Rebuilt <slug> (no closing block)` lines, the second prints none.

If either audit looks wrong, `BLOG_REBUILD_STALE_PAGES=off` in Render stops the
page rebuild entirely and leaves every stored page as it is.



1. **Give the 96 button-less pages a closing block** — a third of the corpus
   currently persuades and stops. This is the largest conversion gain available,
   and it is a template fix plus a targeted re-render.
2. **Route the 191 provider links through `/ai-jobs/apply/<id>`** — makes every
   existing click countable. `ctaTarget()` already prefers the tracker when there
   is no direct URL; it needs to stop preferring the direct URL when there is one.
3. **Report `apply_no_destination` per tenant in the portal** — a "fix these
   offers" list, which is a renewal conversation with a number attached.

None of the three should be done by quietly re-rendering the corpus. Each needs
the kill switch respected and a before/after diff the owner can read.

### What the measurement changed

**`btn=2` was the wrong metric.** A page can carry two buttons and still send the
reader nowhere: 56 pages have both buttons pointing at `/ai-jobs` because their
post has no `opportunity_id`, so `ctaBlock()` has no offer to name and no
destination to resolve. Those pages now say so honestly instead of 404ing, but
they cannot convert — they are one `opportunity_id` away from being both a working
destination and a measurement point (`/ai-jobs/apply/<id>`).

**A bug the census exposed, fixed here.** The no-destination branch returned the
full block *before* the `variant: 'top'` check, so a page with an unlinked offer
printed the same `<h2>` and the same "no link configured yet" sentence above the
article and again below it. `ctaBlock()` now honours the compact variant in that
branch, `repeatsFallbackNote()` lets the boot restore repair the 56 pages written
while the bug was live, and both `test:blog-html` and `test:boot-convergence`
assert it.

**Content observation, not fixed.** The sampled page renders the article title and
a `Published … | Reading time: 3 min` line **twice** — the template's own, then a
copy that lives inside `blog_posts.content`. That pollution predates this work and
no page rebuild can fix it: it would mean rewriting `content`, the one column every
repair path deliberately leaves alone. It needs a separate, reviewed migration.

## Next slice, in the order the numbers argue for

1. **56 pages with no offer link.** Match those posts to their `opportunity_id`.
   Each match turns a dead button into `/ai-jobs/apply/<id>` — a real destination
   *and* a click this server can count. Cheapest revenue-adjacent work available.
2. **378 provider-direct buttons.** The reader converts; the server learns nothing.
   Routing them through `/ai-jobs/apply/<id>` (which already records the click and
   redirects) makes the blog a measurable channel instead of a guess.
3. **The duplicated title inside `content`.** Visible on live pages, needs a
   deliberate content migration, not a page rebuild.
