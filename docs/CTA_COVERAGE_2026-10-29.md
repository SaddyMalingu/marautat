# The button that answered with JSON

**Shipped:** 2026-10-29
**Surface:** `routes/aiJobs.js` (`GET /ai-jobs/apply/:id`)
**Test:** `npm run test:apply-fallback` (22 checks)
**Audit:** `npm run audit:cta-coverage` (read-only, against a live site)

## What the log showed

```
19:57:20  GET /ai-jobs/apply/39fa5490-… 404 - 380ms
```

Probing that URL returned `{"error":"No destination configured for this offer"}`.
A real reader had pressed a button on a page they read to the end, and the site
answered with raw JSON. The click was not recorded either — the route returned
before it reached the tracking — so the leak was invisible in the one place that
should have shown it.

## What it does now

| Before | After |
| --- | --- |
| `404 {"error":"No destination configured for this offer"}` | a page: "Applications for this one are not open yet", the offer's name, a link back to the article and to `/ai-jobs` |
| the click vanished | counted as `apply_no_destination` (or `apply_bad_destination`), and recorded on the offer funnel as `apply_click` with `unavailable: true` |
| a missing offer dropped silently | counted as `apply_missing`, then the same 404 JSON for API clients |

A working destination still gets a `302`, and the destination is still validated
(`http`/`https` only, and only if it is trusted) before it is used. `noindex` on
the fallback page, so it cannot compete with the real offer in search.

The reason this matters commercially: an "unavailable" click is the most
valuable click in the system. It is a reader who wanted to buy something the
business forgot to connect. It now appears in the tenant's numbers instead of
looking like nobody was interested.

## The number that came out of looking

`npm run audit:cta-coverage` against production:

```
Blog index: 200, 308 article links

Button goes straight to the provider .... 191 (62%)
Button goes through this site ........... 0 (0%)   measurable
No button at all ....................... 117 (38%)   cannot convert
  ...of those, no CTA block at all ..... 96 (31%)   template never added one
```

Three facts, none of which was visible from the database:

1. **Not one page routes its button through this site.** Every tracked click the
   portal reports will come from future pages, hubs, or offer pages — never from
   the 191 that already exist. The CTR figure for those pages is not "0%", it is
   "not measured", which is why the endpoint returns `clicks_note`.
2. **117 pages (38%) have no button at all**, so they cannot convert however good
   the writing is. **96 of those have no closing block whatsoever** — the
   `contentJourney` "skills/salary" pages were generated by a template that never
   learned about the CTA.
3. The two populations want different fixes. The 191 need a tracked redirect; the
   96 need a closing block. Those are template changes and therefore re-render
   those pages (`content` untouched, `BLOG_REBUILD_STALE_PAGES=off` still applies).

## Next slice, in the order the numbers argue for

1. **Give the 96 button-less pages a closing block** — a third of the corpus
   currently persuades and stops. This is the largest conversion gain available,
   and it is a template fix plus a targeted re-render.
2. **Route the 191 provider links through `/ai-jobs/apply/<id>`** — makes every
   existing click countable. `ctaTarget()` already prefers the tracker when there
   is no direct URL; it needs to stop preferring the direct URL when there is one.
3. **Report `apply_no_destination` per tenant in the portal** — a "fix these
   offers" list, which is a renewal conversation with a number attached.

None of the three should be done by quietly re-rendering the corpus. Each needs
the kill switch respected and a before/after diff the owner can read.
