Tenant onboarding — how a new client gets in, and what they can do

Status: working end to end as of 2026-10-25, after the ensureAlphadomeTenant guard. Read this before demoing "we can onboard you".

The one rule

A tenant is one identity with two shells:

| Where | What it is | Who uses it | |---|---|---| | public.bot_tenants | real table, portal credentials (portal_token, status) | /tenant/session/login, session cookie | | alphadome.bot_tenants | real table, same id, WhatsApp + AI + SMTP credentials | webhook lookup, get_tenant_by_wa, get_catalog |

Everything else in public named bot_* is an auto-updatable view over alphadome, so the portal can read and write the bot's tables without knowing the schema exists. Those tables carry bot_tenant_id … REFERENCES alphadome.bot_tenants(id).

Therefore: a tenant that exists only in public can log into the dashboard and cannot save a single product, FAQ or order. PostgREST answers 23503 foreign_key_violation; the reads just look empty, so the failure is silent until someone tries to save.

The chain, step by step

  1. Discovery form — GET /discovery → public/client-discovery-form.html,

    2. posts to POST /discovery. Required: name, email, phone, business_name, industry, team_size, whatsapp_usage, revenue_target, ownership_interest, timeline, budget. Stored in public.discovery_submissions; falls back to logs/discovery_submissions.jsonl if the table is unavailable. The phone is normalised to 2547XXXXXXXX on the way in.

  2. Owner approval — POST /admin/api/discovery/submissions/:id/approve

    3. (x-admin-key). Refuses a submission without a usable Kenyan mobile, mints a portal_token, creates or updates the tenant, and now also guarantees the alphadome twin (ensureAlphadomeTenant). Idempotent: an already-approved card returns the same link instead of minting a new one.

  3. Invite — POST /admin/api/tenants/:tenantId/portal-link issues/rotates

    4. the same kind of token for tenants that never came through the form (Kassangas, manual adds). Response includes portal_url (/tenant-dashboard?t=<token>&phone=<phone>), a wa.me hand-off and the message text. catalogue_warning is null when healthy — a string means the invite works but the catalogue cannot be saved yet.

  4. Sign-in — POST /tenant/session/login with { key: <token> }. The token

    5. identifies one tenant; a different tenant_phone is refused 403. Session lives in an HttpOnly cookie (/tenant/session/me rehydrates it).

  5. Dashboard — /tenant-dashboard (admin/tenant_dashboard.html), gated by

    6. tenantDashboardAuth. Features and the table each one actually writes:

| Tab | Endpoint | Backing data | |---|---|---| | Product Catalog | /tenant/catalog | public.bot_products → alphadome (FK ← twin) | | Orders | /tenant/orders | public.bot_orders → alphadome | | Bot Training | /tenant/training | public.bot_training_data → alphadome | | Bot Config | /tenant/bot-settings | alphadome by phone (404 if no twin) | | SMTP | /tenant/smtp | public.bot_tenants (mirrored) | | Writer's Flow → Research & Outreach | /tenant/wf/campaigns | public.wf_campaigns (tenant_id) | | Writer's Flow → Blogger | /tenant/blogger* | public.site_tenants + opportunities + blog_posts |

Writer's Flow is the one surface that is entirely public: it lazily creates public.site_tenants from the tenant's client_phone. It works for a tenant with no alphadome row — which is exactly how the half-tenant bug survived a dashboard review.

  1. WhatsApp — a client is reachable only once

    2. whatsapp_phone_number_id (primary) or client_phone (fallback, exact string) resolves. The twin is born with whatsapp_phone_number_id = "pending:<uuid>" and an empty token, so nothing can route to it and every check reads "not configured". Entering the real Meta phone id + token in Bot Config writes public, and bot_tenants_mirror copies it onto alphadome (NULL never overwrites).

What the guard does

ensureAlphadomeTenant(row) in server.js:

  • looks the twin up by id first — no-op when it exists, so live credentials

    • are never overwritten by a second invite;

  • otherwise inserts alphadome.bot_tenants with the same uuid, the normalised

    • phone, is_active copied, and metadata.awaiting_whatsapp = true;

  • on 23505 (phone already held by a different uuid) it refuses and names the

    • row to merge, instead of splitting the identity further.

insertBotTenantRecord mints the uuid itself and calls the guard before the public insert, so a phone already claimed in alphadome fails with nothing half-created; a failed public insert releases the reservation.

Verify it (no database client needed)


node scripts/test_discovery_approvals.mjs        # 122 static checks, incl. birth order
node scripts/test_smoke_tenant_onboarding.mjs    # stubbed end-to-end, incl. FK failure case
node scripts/smoke_tenant_onboarding.mjs --key=<ADMIN_PASS> --tenant=<name> --issue --write

--write saves one training row through the dashboard API and deletes it again, which is the only check that proves the foreign keys are satisfiable for that tenant. A public-only tenant fails it with 23503.

Why a run can still overshoot the budget by seconds (fixed after 2c5405c). A dashboard run on 2026-10-22 13:54 UTC (offer ed024a64, 90 s budget) returned nine pages in 109.3 s with [GEN] AI budget spent (108s of 90s). The cause was one call, not the loop: the openrouter/free attempt started with 12.8 s of budget left and answered 30.7 s later — almost exactly BLOG_AI_TIMEOUT_MS (30 s). Clamping the axios timeout to the remaining budget was not a bound at all, because in Node that timeout measures socket inactivity: an upstream that trickles its response keeps the socket "active" and the value is never reached. ai() now arms an AbortController for min(BLOG_AI_TIMEOUT_MS, remaining) and destroys the socket itself when it fires, so a stalled or trickling provider is cut at the deadline ([AI] openrouter <slug> aborted after Ns — time box spent). Regression test: test:ai-providers → "a slow provider is cut at the deadline, not at its own pace" (1500 ms budget against a stub that needs 5000 ms must return in < 3 s, and an abort stays transient, never fatal). [GEN] Done: now ends the run with posts in Ns of Ms budget, so the host log alone proves the ceiling.

  3. The router slug is time-boxed. openrouter/free picks an upstream per

    4. request and held the full attempt timeout on both 13:55 and 18:03, so it is capped at BLOG_ROUTER_MODEL_CAP_MS (8 s) like the last resort it is.

Providers are tried in order — OpenRouter → Gemini → Groq → Cerebras → Mistral → OpenAI → HuggingFace — so any single key is enough. The journey only aborts when every provider it could try failed on auth/billing (401/402/403, "no remaining credits"). Within a provider, the models are a list too (OpenRouter's free slugs, Gemini's two flash aliases, Groq's three), and a 404/silent alias advances to the next one instead of ending the run.

The keys live on the host, not in the repo. Re-running is safe, and why that matters

If the apply grid shows A. note: keeper already in public, B. columns to add: 0 and E. promote keeper: already present, you are looking at a second run: an earlier run already committed. Every section is written to be re-run, so nothing is damaged — but three things are worth knowing.

  1. The first grid is gone. The report table is dropped and recreated per run.

    2. Verify the end state with _03_verify.sql instead of trusting the surviving grid.

  2. **C. tombstone prints the phone before the update.** On a re-run it shows

    3. merged:<id> as the incoming value, which looks like the tombstone failed. It did not; it already happened.

  3. The merge note is appended once only. It used to append [merged into …]

    4. on every run, stacking the marker (found on the 2026-10-25 re-run). The UPDATE now checks position(marker in description) > 0 first.

Rollback

The whole script is one transaction, so a failed guard rolls back by itself. After a successful apply the reversible pieces are:


DROP VIEW IF EXISTS public.bot_orders, public.bot_products, public.bot_product_images,
