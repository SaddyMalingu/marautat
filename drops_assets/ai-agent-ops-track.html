Browser Actor Runtime (MoreLogin)

AlphaDome agents can now act on the open web through a named, isolated, fingerprinted browser identity per tenant — brokered by this server, attached over CDP, leased, and audited.

Status: implemented, tested, and verified live (2026-10-31). 101 assertions pass offline (no MoreLogin install, no browser, no database), and the adapter has been exercised against MoreLogin Client 2.69.0.0 + ml-cli 2.8.4 on Windows x64.

Architecture


 agent (ABOSS worker / kernel / any HTTP client)
   │  x-agent-key + tenant slug
   ▼
 POST /api/agents/browser/sessions        routes/browserActors.js
   │                                      ├─ identity.js   tenant -> envId (map | table | default)
   │                                      ├─ sessions.js   one lease per profile, TTL, token
   │                                      └─ runtime.js    start / close / phones
   ▼
 utils/browserActor/moreloginClient.js
   ├─ transport "cli"  -> ml-cli env start --env-id …   (port found via IPC pipe)
   └─ transport "http" -> POST 127.0.0.1:<port>/api/env/start
   ▼
 MoreLogin profile (fingerprint + proxy + cookies, one per tenant)
   ▼  debugPort
 utils/browserActor/cdp.js  ->  CDP over WebSocket (Node 22+, no npm dependency)
   ▼
 page facts: title, description, headings, text, links, form/button counts

Why this shape:

  • ml-cli is the default transport, not the Local API. The client's port is not stable between launches; ml-cli discovers it over \\.\pipe\MoreLogin-cli. Hard-coding --port 40000 would work on one host and silently fail on the next, so the adapter only forwards --port when an operator explicitly sets MORELOGIN_PORT. The direct HTTP transport exists for verification and for hosts where the port is pinned.
  • Both transports return one normalised shape. MoreLogin answers debugPort as a string ("9222"). That is parsed once, in normalizeStartResult, so every caller attaches with a number.
  • No Puppeteer/Playwright dependency. The few CDP calls an agent needs are ~150 lines over Node's built-in WebSocket. A solver that needs the full surface can still attach Puppeteer to browserURL — the endpoint is returned as-is.
  • Leases are in memory, audit is in Postgres. A lease is a runtime fact; the audit table answers "who drove whose profile, when, from which agent".

Driving it from an agent

In-process (kernel / ABOSS script) — no HTTP hop:


import { capturePage } from '../utils/browserActor/cdp.js';
import { createMoreloginClient } from '../utils/browserActor/moreloginClient.js';
import { createBrowserRuntime } from '../utils/browserActor/runtime.js';

const runtime = createBrowserRuntime({ client: createMoreloginClient() });
const started = await runtime.startProfile(envId, { headless: true });
try {
  const page = await capturePage({ host: started.host, port: started.debugPort, url });
  // page.title, page.text, page.links …
} finally {
  await runtime.closeProfile(envId);
}

Full control (Puppeteer / Playwright) — attach to the port the lease returned:


// Puppeteer
const browser = await puppeteer.connect({ browserURL: attach.browserURL });

// Playwright
const browser = await chromium.connectOverCDP(`http://${attach.host}:${attach.port}`);

Then keep the lease alive while you work:


curl -s -X POST "$BASE/sessions/$SESSION_ID/heartbeat" \
  -H "x-agent-key: $AGENT_API_KEY" -H 'content-type: application/json' \
  -d "{\"leaseToken\":\"$LEASE_TOKEN\",\"ttlSeconds\":900}"

If the process dies, the lease expires on its own (default 15 min, max 4 h) and the next agent can take the profile. No reaper timer is needed: expiry is enforced at every read.

Security model

  • Fail closed. No key configured → 503. Wrong key → 401. Comparison is constant-time.
  • One tenant, one profile, one holder. Binding is explicit; a profile can only be leased once at a time, and only the holder's token can heartbeat or release it.
  • Tokens never persist. leaseToken is returned to the creator only and never appears in list/detail responses. A Cloud cdpUrl is returned once, to the creator, and is never written to the audit row or a log line. redact() strips api-key/token from every diagnostic string.
  • SSRF guard. POST /capture accepts only http:/https: absolute URLs, max 2048 chars.
  • Tenant scoping on reads. GET /sessions/:id for another tenant's session returns 404, not 403 — no existence oracle.
  • RLS on. Both tables have RLS enabled with no anon policy; only the service role touches them.

Operator runbook

Host prerequisite: the MSVC runtime

ml-cli.exe imports exactly one non-OS DLL — VCRUNTIME140.dll. On a host without the Visual C++ runtime it dies at startup with 0xC0000135 (STATUS_DLL_NOT_FOUND) and reports nothing on stdout, which is why the vendor bootstrap fails with "Downloaded ml-cli could not report a valid version".

Two supported fixes, in order of preference:

  1. System-wide (needs one UAC approval): install the Microsoft Visual C++

    2. 2015–2022 Redistributable (x64). Most production hosts already have it.

  2. App-local (no elevation): copy a genuine x64 vcruntime140.dll next to

    3. ml-cli.exe in %USERPROFILE%\.morelogin\bin. Verify it first — a 32-bit copy fails differently (0xC000007B, STATUS_INVALID_IMAGE_FORMAT), which is the trap here: VS Code's bundled copy under tools\ is x86.

Check a copy's architecture before trusting it (PE machine type at e_lfanew+4: 0x8664 = x64, 0x14c = x86). Confirm Authenticode=Valid and a Microsoft signer too — the runtime is executable code.

Known limits (v1, deliberate)

  1. The MoreLogin desktop client must run on the same host as the broker. That is the vendor's local-runtime constraint. Cloud runtimes remove it (runtime: "cloud"), but a Cloud cdpUrl is only usable by a worker on that same network — the HTTP API hands it over; it does not proxy the browser session.
  2. Leases are per-process. Two server instances would each keep their own lease table. Fine for the current single-instance deploy; move the broker to Postgres (browser_actor_sessions + a select … for update) before horizontal scaling.
  3. No screenshot/PDF capture yet. One evaluate returns text facts; screenshots are a second CDP call (Page.captureScreenshot) and a decision about storage.
  4. No per-tenant URL allowlist. Any authenticated agent can point a profile at any http(s) URL. Add allowed_domains to browser_identities when a second tenant onboards.
  5. env close falls back to env stop if an older CLI build rejects the subcommand. Both are probed, neither is guessed.

Refer-and-earn: the link is the asset

The offer's referral_url is the CTA, and offerMeta() already resolves destination_url || referral_url || application_url. So an offer published without the tenant's own referral link helps the marketplace for free.

Verified live (2026-10-31): work.turing.com/dashboard/job_referral loads authenticated, but the referral link is not in the DOM until you interact — pickReferralUrl() therefore returned null, and that refusal is the feature: a guessed CTA would send a tenant's traffic nowhere.

Practical consequence: don't scrape the link — inherit it. The Writer's Flow offer form already has a referral_url field (POST /tenant/blogger/offers), so every link a tenant uses is already stored per offer. resolveReferralUrl() reads that history and picks the newest link whose hostname matches the platform (turing.com / micro1.ai), refusing cross-platform matches and lookalike domains — so a Turing link can never land on a Micro1 page. A configured default is used only when the tenant has no history, and only for its own host.

That is deterministic, needs no UI interaction, and needs no new secret.

toOfferDraft() maps a role onto the portal's own offer form: offer_type: 'job' (so the existing career copy in utils/contentJourney.js applies to the referred candidate), status: 'draft' (agent proposes, tenant publishes), the parsed rate as compensation_max in USD, and referral_url from the tenant.

Importing roles as draft offers

Offers are opportunities rows — the portal's own table (POST /tenant/blogger/offers writes the same shape). Four properties hold, each pinned by a test:

  • slug is globally UNIQUE, so it encodes tenant + source + role

    • (malingu-ventures-turing-project-lead-ai-training). Two tenants finding the same role can never fight over one row, and a re-run resolves to the same slug.

  • Re-running creates nothing. Existing rows are skipped (by slug, or by title for

    • hand-made offers) and the planner has no update path at all — which is how a tenant's per-offer referral_url survives every subsequent run.

  • Every row is status: 'draft'. Nothing publishes itself.
  • An unknown tenant slug writes nothing and prints the slugs that do exist, so a

    • typo is visible instead of silently creating orphan rows.

A newly discovered role arrives without a referral link, by design: each link is unique per role. attachReferrals() fills in only what the tenant already holds for that specific role, and reports the rest in needsReferralLink so the tenant can paste them (the offer form already has the field).

Per-role referral capture

A role's own link is read from the live session, one role at a time:

This is a click on the tenant's logged-in account (expand card → referral bonus), not a read, so it lives in its own script behind its own flag instead of inside the collector. Default is plan-only; --apply attaches.

Rules, each pinned by a test:

  • a link is accepted only when it carries a referral token (?ref=, ?code=, /r/,

    • referr, invite) and sits on the marketplace host. /dashboard/job_referral is never accepted, even though it contains the word "referral".

  • pickRoleReferralUrl exists because pickReferralUrl — written for the

    • tenant-level Refer & Earn page — penalises /jobs paths, which is exactly where a per-job link lives. Reusing it captured nothing, and said nothing.

  • an offer that already has a link is a conflict, never an overwrite. The write is

    • additionally guarded by .is('referral_url', null), so a race with the tenant pasting a link by hand cannot clobber it.

  • the same link may not land on two offers.
  • a modal with no confident pick writes nothing and keeps its candidates in

    • tmp/referrals.json — that is a human decision, not an agent's.

It needs the profile map, which is not in .env yet (earlier runs passed it inline in the shell, so nothing was persisted):


BROWSER_ACTOR_PROFILES={"malingu-ventures":"<morelogin envId>"}

Without it the script stops with profile_unmapped and writes nothing — the identity layer refuses to guess which browser belongs to which tenant.

The sealing key, operationally

TENANT_SECRET_KEY is the only secret this feature needs, and it has one rule that is easy to get wrong: the portal seals, the runner opens, so both must hold the same value. A mismatch is silent until a run starts and then reports reconnect_required, which looks like the tenant's fault.


node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"   # generate
npm run secrets:check                                                     # verify this host

secrets:check prints the sha256: fingerprint of the configured key(s) and, per tenant, whether their stored key opens — with current, with the retiring key, or not at all. Compare the fingerprint in the Render log with the one on the operator machine; equal fingerprints mean equal secrets, and neither side has to reveal it. Exit code is 1 if any tenant cannot be opened, so it can gate a deploy.

Rotation is a three-step move, supported by TENANT_SECRET_KEY_PREVIOUS:

  1. TENANT_SECRET_KEY_PREVIOUS=<old> and TENANT_SECRET_KEY=<new>, on the portal and

    2. every runner host.

  2. Deploy. Old seals keep opening (the runner logs that the tenant is on the retiring key);

    3. new connects seal with the new key.

  3. Once secrets:check reports zero on the retiring key, remove

    4. TENANT_SECRET_KEY_PREVIOUS.

Without step 3 the old key stays valid forever, which defeats the point of rotating.

Handing out a bundle that required SUPABASE_SERVICE_ROLE_KEY would have been the largest security regression in this repo — one careless tenant screenshot and every tenant's data is writable. So the privileged half of the capture moved to the server, behind the worker token:


tenant machine                                    portal

Rules that keep the new endpoints safe rather than merely convenient:

  • The tenant comes from the token, never from the body — same as the claim path.
  • The context refuses anything but the tenant's own local profile. A tenant worker cannot be

    • pointed at the operator's hosted browser, and a cloud profile is refused with "press Capture again".

  • The result payload is untrusted input. Titles and bodies are bounded, unknown fields dropped,

    • and a javascript:/file: URL is discarded rather than stored and rendered later.

  • Every link is re-verified server-side before it is attached, so a compromised worker cannot

    • inject a link that pays somebody else.

  • A closed run cannot be written to (409), so a retry cannot double-insert.
  • A batch is bounded, and a 413 is split, not swallowed. On 2026-11-04 a 120-role Turing run

    • re-sent everything it had on every flush: the last post was ~400 KB, Express answered PayloadTooLargeError, and the run closed 120/120 · failed with no links written. So /api/agent carries its own 12 MB parser (mounted before the global one — every other route still refuses >100 KB), the runner advances a postedCount cursor instead of re-sending, and a chunk that is refused with 413 is halved and retried before it is treated as a failure.

  • A run ends on /finish, and only there. If some batches landed and the last did not, the run

    • closes as partial — neither success nor failure, because either word would hide the number that matters: how many links actually reached the portal.

  • No MoreLogin key in the context. A stolen wkr_ token therefore buys the ability to burn that

    • tenant's own daily starts — not control of their marketplace accounts.

On 2026-10-23 the tier held four keys and served no copy — HF 402, Gemini 429 daily quota, four of five OpenRouter free slugs 429/404 — and every click still came back 200 in ~31 s. This check asks the provider directly, through the same ai() walk that serves Writers, Share, Review and replies, so its verdict cannot drift from production:


npm run check:ai-key                       # every provider that has a key
npm run check:ai-key -- --only=gemini      # just one
npm run check:ai-key -- --key GEMINI_API_KEY=AIza...   # no file, no .env needed

It prints the masked key it used, then per provider either SERVED in 0.4s — "OK" or the chain's own status/body plus the fix (out of credits, key rejected, daily quota spent, slug retired, no answer inside the time box). Exit code 0 = at least one provider wrote copy, 1 = none did — so it can gate a deploy.

Sequence when the tier is already keyed — the usual case, because the keys are Render variables: reveal the var in Render → Environment, then run npm run check:ai-key -- --only=<provider> --key <VAR>=<value> until it says SERVED or names the account problem. If it names quota, wait for the reset (Gemini: midnight Pacific, 10:00 EAT) or change project/provider — redeploying does not help. Sequence for a brand-new key: create it → probe it with --key → add the same var on Render → Manual Deploy (auto-deploy is off on this host) → boot log must say gemini=true → click Review on the Writers tab and confirm the API body says mode:"polished" → npm run verify:writers-flow.

GET /tenant/blogger now returns voice (id, label, source, brand, industry) and voiceOptions (all six profiles with a one-line essence), and the Writer's Flow → Blogger tab shows a "Your writing voice" panel with a picker, Save voice, and Use assigned. POST /tenant/blogger/voice writes the choice to site_tenants.metadata.voice, merging the existing jsonb instead of replacing it, and accepts { voice: null } to clear. metadata is used deliberately: it already exists on every deployed site_tenants row, so a tenant can pick a tone without waiting for a migration; a host that somehow lacks the column answers 503 naming migrations/2026-10-11_add_site_tenants_multitenant.sql rather than pretending it saved. Unknown ids are refused with the allowed list, and the full prompt block is never sent to the browser — only the label, source and market. Proof: npm run test:tenant-voice (23 checks).

AI Jobs & Mercor Referral Engine

Overview

The AI Jobs subsystem is an additive feature that adds an SEO-driven opportunity discovery and Mercor referral engine to the existing AlphaDome platform. It operates independently without affecting existing functionality.

Architecture


AlphaDome

│   ├── Authentication

    ├── Category taxonomy

    ├── SEO pages
    ├── Analytics tracking
    └── Admin interface

Database Tables (New)

All tables are in the alphadome schema and do not affect existing tables:

  • opportunity_sources - External providers (Mercor, etc.)
  • opportunity_categories - Professional categories with referral links
  • opportunities - Individual job listings
  • opportunity_events - Analytics events
  • referral_links - Centralized referral URL configuration

Routes

  • GET /ai-jobs - AI Jobs landing page
  • GET /ai-jobs/mercor - Mercor opportunities page
  • GET /ai-jobs/mercor/:categorySlug - Category page

  • GET /api/opportunities/:id/apply - Track click and redirect to Mercor

SEO

Referral URL Resolution

The system uses a three-tier referral URL resolution:

  1. Job-specific URL (highest priority) - Individual Mercor job referral link
  2. Category URL - Category-level Mercor referral link
  3. General URL (fallback) - General Mercor referral link
